# BistroGuard AI — Restaurant Support & Operations Agent

A restaurant support and operations agent built with **Python, FastAPI, Groq LLM, SQLite, and ChromaDB**.

BistroGuard AI handles common restaurant support tasks such as checking orders, answering policy-related questions, placing new orders, creating support tickets, and handling customer complaints.

The project also includes basic security checks, RAG-based policy search, session history, and logs for tracking what the agent did during a request.

---

- AI-based restaurant support

## How the System Works

The basic flow is:

```text
Customer
   ↓
FastAPI API
   ↓
Security Check
   ↓
Complaint / Request Classification
   ↓
Agent
   ├── Order Tools
   ├── RAG / Policy Search
   ├── Support Ticket
   └── New Order
   ↓
SQLite / ChromaDB
   ↓
Response + Execution Logs
```

The LLM is used for understanding the request and deciding which tool or workflow is needed. Actual order information and customer authorization are handled by the application and database instead of being generated by the model.

---

## Main Tools

The agent currently works with the following tools:

### `place_new_order`

Used when a customer wants to place a new order.

It reads the requested items, calculates the order total, creates an order ID, and stores the order in SQLite.

### `get_order_status`

Returns the current status and delivery information for an order.

The tool also checks whether the requested order belongs to the logged-in customer.

### `get_order_details`

Returns the details of a particular order, including its items and other stored information.

### `list_customer_orders`

Returns the orders associated with the current customer when the customer does not provide a specific order ID.

### `search_knowledge_base`

Searches restaurant policy documents stored in the knowledge base.

The project currently includes policies related to:

- Cancellation
- Payment
- Delivery
- Restaurant hours

### `create_support_ticket`

Creates a support ticket when a complaint needs to be escalated.

A SHA-256 based idempotency key is used so that the same request does not create multiple tickets.

---

## RAG / Knowledge Base

BistroGuard uses **ChromaDB with TF-IDF based embeddings** for policy retrieval.

The policy documents are stored in SQLite and synced into the ChromaDB collection.

A similarity threshold is used before returning a policy result. This helps avoid returning unrelated documents when the query does not match the available policies.

The project also handles zero-vector queries. If a query has no matching vocabulary, the system returns no result instead of sending an invalid vector to ChromaDB.

## Security

There are two main security checks in the application.

### Prompt Injection Protection

User messages are checked before they reach the LLM.

Examples of blocked requests include attempts to:

```text
ignore previous instructions
reveal system prompt
reveal API key
dump database
```

The request is rejected when a matching unsafe pattern is detected.

### Customer Authorization

Customers cannot access another customer's orders.

For example:

```text
CUST-42 → ORD-1001
```

is rejected when `ORD-1001` belongs to another customer.

The authorization check is performed by the application using the customer ID stored with the order.

---

## Support Ticket Workflow

Some messages are treated as complaints instead of normal information requests.

For example:

```text
My payment was deducted but my order failed.
```

The complaint workflow identifies the issue and can create a support ticket automatically.

The ticket creation process uses a SHA-256 idempotency key. If the same request is sent again, the existing ticket can be returned instead of creating another ticket.

---

## Database

The project uses SQLite for local persistence.

Some of the important data stored in SQLite includes:

```text
orders
support_tickets
session_messages
knowledge_base
```

Conversation history is stored using a `session_id`, which allows the agent to maintain context between messages.

## API

The main chat endpoint is:

```http
POST /api/agent/chat
```

The response contains separate sections for:

```text
llm_response
authoritative_operational_data
automation_workflow_triggered
observability_trace
```

This makes it easier to see the difference between the model's response, actual database information, automated workflows, and tool execution logs.

The project also provides an interactive web console through:

```http
GET /
```

## Running the Project

### 1. Clone the repository

```bash
git clone https://github.com/ishu-anand-1/Bistroguard-agent.git
cd Bistroguard-agent
```

### 2. Install dependencies

```bash
pip install -r requirements.txt
```

### 3. Create the environment file

Create a `.env` file in the project root:

```env
OPENAI_API_KEY=your_groq_api_key_here
OPENAI_BASE_URL=https://api.groq.com/openai/v1
LLM_MODEL=openai/gpt-oss-120b
SIMULATE_ORDER_API_OUTAGE=false
```

**Do not commit the `.env` file or your actual API key to GitHub.**

### 4. Run the tests

```bash
python -m pytest -v
```

Run the agent evaluation:

```bash
python -m tests.test_agent_eval
```

### 5. Start the server

```bash
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

Then open:

```text
http://127.0.0.1:8000/
```

## Failure Handling

The project also includes a few failure scenarios for testing.

### Order API Failure

Order-related tools can simulate an external API outage.

The agent returns the error instead of making up an order status or delivery ETA.

### RAG Query With No Match

If the query has no vocabulary overlap with the stored documents, the RAG system returns no matching policy.

### Unauthorized Order Access

If a customer tries to access an order belonging to another customer, the request is rejected.

## Notes

This project is mainly focused on building a reliable restaurant support agent where the LLM handles natural-language understanding while application code remains responsible for operational data, authorization, database operations, and security checks.

The current RAG implementation uses TF-IDF rather than a neural embedding model to keep the setup lightweight and avoid additional model-download requirements.
